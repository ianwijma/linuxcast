# Raycast website and client research

Research date: **22 October 2026**. This document records the publicly documented product, then states Linuxcast's disposition. It is not a claim that Raycast's proprietary implementation was executed, inspected, or reproduced. The approved scope is in [PLAN.md](../PLAN.md); implementation work follows the [roadmap](../implementation/ROADMAP.md), [AI contracts](../architecture/ai.md), and mandatory [design specification](../design/DESIGN.md).

## Evidence and version rules

The current [manual](https://manual.raycast.com/quickstart) and [v2 introduction](https://manual.raycast.com/new-in-v2) are the primary functional baseline. The latter describes a rebuilt macOS client, revised search/indexing, compact presentation, richer shortcuts, conversation branching, projects, agents, skills, and personalization. Historical v1 pages and beta announcements must not override current documentation. “Presets” are now Agents; older AI folders are now Projects. These renames do not establish compatibility with Linuxcast formats.

The manual mixes macOS and Windows behavior, often through platform controls. A feature on a current page is evidence of documented behavior, not proof of availability on both platforms. Windows Run and Games are explicitly Windows-oriented. Apple Contacts, EventKit, AppleScript, Shortcuts, Stage Manager and Apple-specific share interfaces need Linux equivalents or a documented platform exclusion. Cloud Sync remains described as beta; shared team Skills are marked coming soon. Never turn a preview into a release acceptance claim.

Sources were read through official documentation and official websites. No native Raycast process was run; no binary decompilation, traffic inspection, timing measurement, purchased subscription, or end-to-end authentication test was performed. Screenshots embedded in sources support the separate visual research, not runtime verification. Collapsed documentation sections, OS-specific edge cases, private organization pages, actual Store packages, and every third-party integration were not exhaustively executed. The [source fragment](sources-ai.json) records exact URLs and these evidence classes. Recheck changing authentication, terms, model catalogs, and platform support during implementation.

## AI model supply and service boundaries

| Source | Documented Raycast behavior | Linuxcast decision |
| --- | --- | --- |
| [Local models](https://manual.raycast.com/ai/local-models) | Ollama lifecycle/discovery and capability-aware use in chat/commands; some features and hosted tools remain outside local inference. | Ollama is a first-class selectable global provider. Offline claims require all requested tools, memory processing and attachments to stay local too. |
| [Custom providers](https://manual.raycast.com/ai/custom-providers) | Local provider configuration, model metadata and direct compatible requests; invalid updates retain previous configuration. Web/image-search tools can have independent configured services. | Validated native configuration, keyring secret references rather than plaintext credentials, explicit capabilities and opt-in network tools. Never mistake compatible syntax for identical features. |
| [Extension models](https://manual.raycast.com/ai/extension-models), [developer API](https://developers.raycast.com/ai/provide-ai-models) | Extension-supplied model discovery/streaming, setup/permission states and cached catalogs; streaming parts and model capability declarations. Restrictions differ from hosted models. | Provider-plugin contract through the broker; extension isolation and explicit credential ownership. Model providers cannot bypass the active-selection policy or obtain other providers' keys. |
| [Bring your own key](https://manual.raycast.com/ai/bring-your-own-key) | OpenAI/Anthropic/Google keys and direct OpenRouter have different routing/catalog behavior; hosted tools may still consume Raycast services. | Direct-to-selected-provider requests, clear endpoint and billing ownership; no Linuxcast proxy required. OpenRouter is mandatory. |
| [Bring your own subscription](https://manual.raycast.com/ai/bring-your-own-subscription) | Raycast documents local original Codex/Claude CLI sign-in and direct inference with provider account/usage status. This is evidence about Raycast's product, not transferable authorization for a new app. | Use only official supported SIWC/Codex/Copilot paths and permitted Claude integration. See [provider rules](../architecture/ai.md#provider-and-plan-routes). Never harvest CLI OAuth credentials. |
| [Privacy/security](https://manual.raycast.com/ai/raycast-ai-privacy-security) | Feature-specific processing and storage differ; memory, hosted tools, attachments and sync can involve services even when a response uses another provider. | Per-operation data destination disclosure and source preview. Local provider selection alone cannot justify “nothing leaves this computer.” |

Image generation, online research/search and arbitrary external integrations are **provider/tool-dependent services**, not guaranteed properties of a text model. Linuxcast must support representing and configuring these capabilities, showing a clear unavailable state when the selected backend/tool cannot perform them. It must not secretly route to another model, invent a Raycast credit account, or promise proprietary backend parity. Reference tools should make the service boundary explicit; local-first storage and workflow execution remain v1 requirements.

## Cloud, organizations, enterprise and mobile

[Cloud Sync](https://manual.raycast.com/cloud-sync) documents category selection, device management, progress and deletion controls for settings and user content, with exclusions such as clipboard history, credentials and script bodies. Encrypted transport/storage claims do not establish end-to-end encryption. Linuxcast v1 uses native local backup and portability; a sync conflict/deletion/encryption protocol needs its own future design.

[Shared team features](https://manual.raycast.com/teams/shared-features) cover private extensions and shared reusable content; shared Skills are explicitly upcoming. [Roles](https://manual.raycast.com/teams/roles-and-permissions) distinguish management, billing and membership. [Enterprise](https://manual.raycast.com/enterprise) adds identity provisioning, SSO/domain controls, device sign-in policies, feature/data restrictions, provider/gateway controls and administration. These are documented but deferred, along with billing administration and organization-hosted distribution.

The manual's mobile navigation lists an iOS keyboard, widgets/controls, Shortcuts and share extension. They are separate platform products, not missing Debian client features. Their cross-device/account dependencies are deferred. macOS-specific hardware integrations and Windows settings/registry operations receive Linux substitutions where meaningful; they are never silently marked implemented.

## Coverage gates for the implementation graph

1. **Local independence:** launcher, search, notes, snippets, quicklinks, calculator, clipboard, local media/OCR, native workflows and settings remain usable without an account or provider. Network rate data and external connectors report stale/offline status.
2. **Platform truth:** test the four target sessions—GNOME 48 and KDE Plasma 6.3, each on Wayland and X11. Record permission denial, missing companion and unsupported functionality. Do not use a successful X11 demo as Wayland evidence.
3. **One AI destination:** Quick AI, commands, translation, optional emoji matching, workflow AI nodes, extension AI, memory and dictation cleanup share the same global provider/model snapshot. Harness execution is an explicitly separate command with visible identity/billing.
4. **State integrity:** cancellation, partial streams, process crashes, stale searches, focus changes, clipboard ownership changes, sleep/resume and model removal cannot appear as completed results or replay side effects.
5. **Extensibility:** native declarative views, command/script interfaces, permissioned tools and visual workflows are tested through complete examples; unsupported third-party packages do not masquerade as compatible installations.
6. **Input boundary:** privileged snippet/Hyper support is optional and disabled by default; extensions and AI cannot subscribe to raw keys. Scope, recovery and manual fallback are release gates.
7. **Design:** all screens, permissions and exceptional states use [DESIGN.md](../design/DESIGN.md), with keyboard navigation, visible focus, light/dark treatment and accessible error/loading states.

The source inventory establishes breadth; executable task cards and feature coverage records establish completeness. Neither this document nor a marketing feature count is evidence that an implementation has passed those gates.
